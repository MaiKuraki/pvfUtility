# 优化记录：从初始版到现在

这份文档记录 pvfUtility 从恢复出可运行版本以来，所有针对**性能、稳定性、数据安全**的改动。

面向的是维护者和想知道"为什么这么改"的开发者。日常使用看 [README](../README.md) 就够了。

---

## 一、总体对比

测试数据来自真实客户端包：

| 项目 | 包大小 | 文件数 | 字符串条目 |
|---|---|---|---|
| 台服（TW） | 212 MB | 367,527 | 750,905 |
| 国服（CN，qf1031） | — | — | 412,184 |

| 指标 | 初始版 | 当前 | 依据 |
|---|---|---|---|
| 打开 PVF 到文件树可用 | 约 12 秒 | **4.4 秒（TW）/ 3.6 秒（CN）** | 日志 `[开包耗时]` |
| ImagePacks2 索引（15 万张图） | 12 秒 | **< 1 秒** | 日志时间戳 |
| 建文件树（36 万文件） | 约 6~7 秒 | **1.5~1.8 秒** | 日志 `[开包耗时]` |

## 二、按主题的改动

### 1. 解密与读包

| 改动 | 说明 |
|---|---|
| 解密算法 Span 化 | 原实现每个 4 字节块都要 `BitConverter.GetBytes` 分配一个数组；改为直接在 `Span<byte>` 上读写。**吞吐 9 → 1 字节/字节分配，速度 3.6 倍** |
| 加密同样 Span 化 | 保存路径，与解密对称 |
| `InitFile` 原地解密 | 原来"读一份 → 解密成新数组"，改为在已有缓冲区上原地解密，每个文件少一次整块分配 |
| 文件数据按偏移顺序读 | 原实现按字典顺序逐文件 `Seek`，等于把整个包做随机读；改为先按 offset 排序再顺序读 |
| 文件表字典预设容量 | 36 万条不预设会经历多次扩容 + 整表 rehash |
| 字符串表 / 字符串链接预设容量 | 75 万条同上 |
| 字符串链接去循环内开销 | `Encoding.GetEncoding` 提到循环外；先按原样查、未命中再 `ToLower` |

效果：读包 2687 ms → 1688~2140 ms。

### 2. 节索引与名称提取

| 改动 | 说明 |
|---|---|
| 节偏移缓存 | 原来每次查节都从文件头扫到文件尾；改为首次扫描后缓存 `int[]`，后续 O(节数) |
| 名称提取走节表 | `GetNameText` / `GetNameByLabel` / `GetNameByLabels` 同样改走节表。**单文件从 O(token 数) 降到 O(节数)** |
| 修正 `GetSectionIntArray` 偏移 | 原实现把字符串 ID 当字节偏移用（明确 bug），改为使用 `FindSectionIndex` 找到的真实位置 |
| 节解析加深度上限 | 损坏文件可能造成无限递归，加 256 层上限 |

### 3. NPK 图片读取

| 改动 | 说明 |
|---|---|
| 单图按索引读取 | 原来取一张图标要 `ReadNpk` 解析整个包再 `FirstOrDefault`；改为按索引里的 offset/length 只读那一段，失败回退整包 |
| 帧数自检 | 快路径解码后比对 `ImgList.Count` 与索引阶段独立读到的 `Count`，不一致判失败回退，避免"不报错但显示错图" |
| NPK 索引解析批量化 | `ReadPath` 原来每个文件名调 256 次 `ReadByte`；改为一次读满 256 字节在内存里异或。索引区一次读 264 字节记录，第二遍用 `RandomAccess.Read` 一次读 40 字节 |
| 真正并行 | `ParallelReadNpkList2` 原来名不副实（串行 foreach），改为 `Parallel.ForEach` |
| 并发度按磁盘类型自适应 | SSD 4 路、HDD 1 路（机械盘并行随机读更慢）、探测失败 2 路 |

效果：ImagePacks2 索引 12 秒 → < 1 秒。

**验证**：用真实的 2432 个 NPK / 8.8 GB 数据做新旧实现逐条比对，150,707 个条目的 offset/name/count **差异 0**。

### 4. 文件树

| 改动 | 说明 |
|---|---|
| 串行构建并去锁 | 原实现 100 路并行 + 每个路径段 `lock(this)`，36 万文件约 180 万次锁竞争，比单线程还慢；同时存在真实竞态：两个线程同时 `TryGetValue` 未命中时各自 new 节点，`AddTry` 失败的那个继续在孤儿节点上建子树，**导致部分文件不在树上** |
| 复用 StringBuilder | 避免每文件每层重新分配 |

效果：建树 6~7 秒 → 1.5~1.8 秒。

### 5. 预览刷新

| 改动 | 说明 |
|---|---|
| 图标缓存不再逐键失效 | 原来每次文本变更都 `referenceIconCache.Clear()`，而图标只取决于 `PvfFile`、与未保存文本无关。改为切文档/已保存内容变化时才失效 |
| 去正则切行 | `Regex.Split("(?<=\n)")` 改为 `IndexOf('\n')` 手写扫描 |
| 按 `[` 预筛 | 标签行正则要求 `^\s*\[`，行内无 `[` 直接跳过正则 |
| 停手 120ms 防抖 | 原来每次文本变更排一次 Background 刷新（约每帧一次），而一次刷新要重建整棵预览对象树。改为 `DispatcherTimer` 防抖 |

### 6. 繁简转换

| 改动 | 说明 |
|---|---|
| ASCII 快路径 | 纯 ASCII 字符串不存在繁简差异，先扫一遍直接返回，省掉 `StringBuilder` 复制与逐字符哈希 |
| 字符位图预筛 | 从转换表构建 `bool[65536]`，整串没有任何字符在表里就直接返回。**台服包的文本本来就是繁体，查"简→繁"表必然全不命中** |

效果：字符串表 629 → 522 ms，字符串链接 342 → 259 ms。

语义与原实现完全等价：所有字符都不在表里时，逐字符替换的结果就是原串本身。

### 7. SSD 写入保护

| 改动 | 说明 |
|---|---|
| 备份前比对内容指纹 | 文件数 + 各文件 `Checksum`/`DataLen` 的 FNV-1a 聚合（36 万文件约 2~3 ms）。未变直接跳过，一次都不写 |
| 备份间隔 5 → 10 分钟 | 整包重写代价高 |
| 配置写入跳过无变化 | `AppConfig.json` 4.7 MB，序列化后与上次写入比对，相同则跳过 |
| 备份清理 O(n²) → O(n log n) | 原来 `foreach` 套 `Any()` 扫描 |

### 8. 编码诊断

| 改动 | 说明 |
|---|---|
| 解析质量统计 | 每次开包输出：总条数 / 含非 ASCII 条数 / 疑似异常条数。异常率 ≥ 5% 提示编码可能选错 |
| UTF-8 / UTF-16 结构性识别 | UTF-16 先判（0x00 占比 ≥ 25%），UTF-8 用严格解码全通过 |

**已知局限**：简体(936) 与繁体(950) 互相解码同样产生合法汉字，纯统计无法区分，只能靠用户看界面判断。

> 中途试过四版"挑几条文本给人看"，分别挑到文件路径、二进制乱码、资源 key（`3cho_explain_support_960`），全部失败——stringtable 里混着路径、索引段、资源 key、显示文本四类内容，没有可靠规则区分。最终改为整体统计。

### 9. 稳定性

| 改动 | 说明 |
|---|---|
| 未处理异常落盘 | `%LOCALAPPDATA%\pvfUtility\logs\unhandled-*.log`，以前只有弹窗不落盘 |
| WebView2 运行时检测 | 缺失时明确提示，不再白屏 |
| 字符串表加载同步化 | 原来丢进后台 `Task.Run` 后立刻返回成功，UI 一查名称就拿到 null |
| 字符串表加载容错 | 单条损坏跳过而不是整个包失败；尺寸字段加边界校验 |
| `ByteHelper` 释放泄漏 | `LocalFree` 移到 finally |

### 10. 代码结构

| 改动 | 说明 |
|---|---|
| `PvfFile` 拆出 `PvfFile.SectionQuery.cs` | 2406 → 2068 + 359 行，partial 物理拆分，方法签名与调用点不变 |
| `NpkIndexCache` 独立 | NPK 索引缓存从 static 字段收敛为实例成员，切换目录时清空 |
| 去 LINQ（热路径） | `PvfPack.GetFiles` ×2、`GetFileObjs` 改手写循环；`GetItemCodes` 去掉多余 `ToHashSet` 复制 |
| 去死代码 | `ImagePack2Service.SaveToDisk()` 是空方法 |

## 三、验证方式

每一次改动都经过：

1. `dotnet build pvfUtility.csproj -c Release` —— 0 error
2. `scripts/Build-SingleFile.ps1` —— 单文件包验证通过
3. `scripts/Test-RecoveredStartup.ps1` —— 主窗口完整、20 秒无错误窗口
4. 涉及二进制解析的改动，额外用真实数据做新旧实现对比

**没有真实数据验证的改动一律不算完成。**

## 四、已知未做

| 项 | 原因 |
|---|---|
| 数据按需加载 + LRU | 需要 PVF 黄金样本才能验证正确性 |
| `async void` 收敛（163 处） | 影响面大，需要单独一个完整迭代 |
| 树懒加载 | 调研后放弃：`FilePathGetTreeNode`、删除节点、选中转路径、文件计数、书签跳转、搜索定位 6 处功能依赖全树 |
| 数据 Arena（消除 36 万次小分配） | 需要把 `PvfFile.Data` 从 `byte[]` 改为切片类型，影响上百处 |
| ReadyToRun 打包 | 需要联网还原 crossgen 包；实测关压缩无效（启动只快 0.14s，体积涨 280MB） |
